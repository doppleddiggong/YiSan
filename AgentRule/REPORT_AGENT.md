## 리포트 작성 규칙 (Report Writing Rules)

### 1. 리포트 작성 트리거

다음과 같은 요청이 있을 때 리포트를 작성합니다:

- 사용자가 명시적으로 "리포트 작성해줘", "문서 만들어줘", "보고서 작성" 등을 요청할 때
- 중요한 버그 수정, 시스템 개선, 기능 구현이 완료되었을 때
- 복잡한 문제 해결 과정을 문서화해야 할 때
- 학습 목적으로 상세한 분석이 필요할 때

### 2. 리포트 저장 위치

**디렉토리**: `Documents/Planning/Report/`

**파일명 규칙**: `YYYY-MM-DD_문서타이틀.md`

**예시**:
- `2025-11-09_로딩시스템_게스트플레이어_이슈리포트.md`
- `2025-10-30_UYiSanLoading_리팩토링.md`
- `2025-11-02_멀티플레이어_네트워크_최적화.md`

**주의사항**:
- 날짜는 반드시 `YYYY-MM-DD` 형식 사용
- 언더스코어(`_`)로 구분
- **한글 파일명 사용** (가독성 우선)
- 공백 대신 언더스코어 사용
- 영문 파일명도 가능하지만 한글 권장

### 3. 리포트 문서 구조

모든 리포트는 다음 구조를 따릅니다:

```markdown
# [문서 제목]

**작성일**: YYYY-MM-DD
**작성자**: [작성자명 또는 Claude AI Assistant]
**카테고리**: [Network / UI / Gameplay / System 등]
**심각도**: [Low / Medium / High / Critical]

### 4. 필수 포함 요소

모든 리포트는 다음을 **반드시** 포함해야 합니다:

#### 4.1 발생 이슈 (Issue)
- 무엇이 문제였는지
- 어떻게 발견되었는지
- 어떤 영향이 있었는지

#### 4.2 발생 원인 (Root Cause)
- 왜 문제가 발생했는지
- 코드 레벨의 분석
- 시스템 레벨의 분석

#### 4.3 수정 내역 (Solution)
- 어떻게 수정했는지
- 수정 전/후 코드 비교
- 왜 이 방법을 선택했는지

#### 4.4 테스트 가이드 (Testing)
- 어떻게 검증하는지
- 재현 방법
- 확인 로그

### 5. 선택적 포함 요소

다음은 문서 성격에 따라 선택적으로 포함합니다:

- **플로우 다이어그램**: 복잡한 시퀀스가 있을 때
- **비교표**: 여러 옵션을 비교할 때
- **성능 측정**: 성능 개선이 목적일 때
- **학습 포인트**: 교육 목적이 강할 때

### 6. 작성 스타일 가이드

#### 6.1 언어
- **기본**: 한글 (사용자가 한국어로 요청)
- **코드**: 영문 주석 권장
- **전문 용어**: 영문 병기 가능 (예: "서브시스템 (Subsystem)")

#### 6.2 어조
- 객관적이고 기술적
- 명확하고 간결하게
- 단계별로 논리적으로 전개

#### 6.3 코드 블록
- 언어 지정 (```cpp, ```python 등)
- 중요 부분 주석 처리
- 라인 넘버 참조 시 명시 (예: `File.cpp:123`)

#### 6.4 시각화
- ASCII 다이어그램 사용 가능
- Mermaid 다이어그램 권장
- 표 형식 적극 활용

### 7. HonKit 통합

리포트 작성 시 `Documents/SUMMARY.md`에 자동으로 추가되어야 합니다.

**추가 위치**: Planning Reports 섹션

**예시**:
```markdown
## Planning & Reports

* [프로젝트 진행 보고서](Planning/YiSan_프로젝트_진행보고서.md)

### Technical Reports
* [2025-11-09 로딩 시스템 게스트 플레이어 이슈](Planning/Report/2025-11-09_LoadingSystem_GuestPlayer_Issue_Report.md)
* [2025-10-30 UYiSanLoading 리팩토링](Planning/Report/2025-10-30_UYiSanLoading_Refactor.md)
```

### 8. 리포트 작성 프로세스

사용자가 리포트 작성을 요청하면 다음 순서로 진행합니다:

```
1. 문제 파악
   ↓
2. 관련 코드 분석
   ↓
3. 문제 원인 진단
   ↓
4. 해결 방안 도출
   ↓
5. 리포트 문서 작성
   ↓
6. Documents/Planning/Report/ 에 저장
   ↓
7. Documents/SUMMARY.md 업데이트
   ↓
8. 사용자에게 완료 보고
```

### 9. 버전 관리

리포트 문서도 Git으로 관리됩니다:

- 리포트 작성 후 커밋 권장
- 커밋 메시지: `docs: add report YYYY-MM-DD [제목]`
- 예시: `docs: add report 2025-11-09 LoadingSystem GuestPlayer Issue`

### 10. 품질 체크리스트

리포트 작성 완료 전 다음을 확인합니다:

- [ ] 파일명이 `YYYY-MM-DD_제목.md` 형식인가?
- [ ] `Documents/Planning/Report/` 디렉토리에 저장되었는가?
- [ ] 메타데이터(작성일, 카테고리 등)가 모두 입력되었는가?
- [ ] 목차가 작성되었는가?
- [ ] 발생 이슈, 원인, 수정 내역이 모두 포함되었는가?
- [ ] 코드 예시에 주석이 충분한가?
- [ ] 테스트 방법이 명확한가?
- [ ] 학습 포인트가 포함되었는가?
- [ ] SUMMARY.md가 업데이트되었는가?
- [ ] 문서 버전과 최종 수정일이 기재되었는가?

### 11. 예외 사항

다음 경우에는 간소화된 리포트를 작성할 수 있습니다:

- **간단한 버그 수정**: 3-5 섹션으로 축약 가능
- **작은 기능 추가**: "시스템 아키텍처" 생략 가능
- **긴급 핫픽스**: 나중에 업데이트 예정 표시

**간소화 예시**:
